1. Project Overview & Why You Built It

What is Movie Opinion Meter? Explain in 2 lines. HOT

It is a web app where users can vote on movies (Masterpiece, Good, Average, Bad), write reviews, and see what percentage of people think what about a movie. For upcoming movies, there is a separate Hype Meter where people vote if they are Excited or Not Excited.

What problem does this project solve? HOT

Normal movie rating sites give you just one number like 7.2/10 — that tells you nothing. My project separates opinions into categories. You can see "40% people think it's a Masterpiece, 30% Good, 20% Average, 10% Bad". This gives a much better picture of what the audience actually thinks.

Also, I separate pre-release hype (will this movie be good?) from post-release opinion (was it actually good?).

Why did you build this project?

I wanted to practice real backend concepts — database design with constraints, query optimization, REST API development, and integrating external APIs. Instead of building a simple CRUD app, I picked a problem that forced me to think about data modeling, aggregation logic, and user experience.

2. Database Design & Models

Explain your data models. What tables do you have? HOT
  • User — Custom user model with email login, email verification flag, profile image URL
  • Movie — TMDB-synced: title, overview, poster, release date, is_released flag
  • Genre — Movie categories (ManyToMany with Movie)
  • Person, Cast, Crew — Normalized people data. Cast links person to movie with character name. Crew links person to movie with job title.
  • MovieVote — 4-category votes for released movies (unique per user+movie)
  • MovieHypeVote — Binary votes for upcoming movies (separate table)
  • MovieReview — Star rating + review text + spoiler flag (unique per user+movie)
  • ReviewLike — Like on a review (unique per user+review)
  • ReviewComment — Comments with self-referential FK for 1-level replies
  • Watchlist — User's saved movies (unique per user+movie)
  • AIRequestLog — Audit trail for every AI request
Why did you make separate tables for MovieVote and MovieHypeVote instead of one table with a flag? HOT

Because they have different vote choices. MovieVote has 4 options (masterpiece, good, average, bad). MovieHypeVote has 2 options (excited, not_excited). If I put them in one table with a column like vote_type, nothing stops someone from accidentally creating a "hype vote" with value "masterpiece" — that's an invalid state.

With separate tables, the database schema itself prevents invalid data. You literally cannot create an invalid combination. This is called "making invalid states unrepresentable".

Also, queries become cleaner: movie.votes always means opinion votes, movie.hype_votes always means hype votes. No filtering needed.

What is unique_together and why did you use it?

unique_together = ("user", "movie") means the combination of user + movie must be unique in the database. So one user can only have one vote per movie, one review per movie, one watchlist entry per movie.

This is enforced at the database level — even if my Python code has a bug, the database will reject the duplicate. This is much safer than just checking in Python code.

Why do you use on_delete=models.CASCADE? Are there cases where you used something else?

CASCADE means: if you delete the parent, delete all children too. For example, if a movie is deleted, all its votes, reviews, comments get deleted too. This makes sense because votes without a movie are useless data.

But for AIRequestLog.movie, I used on_delete=models.SET_NULL. Because if a movie is deleted, I still want to keep the AI usage log for auditing. The log is still valid — it shows who used AI, when, what they typed.

What is the self-referential foreign key in ReviewComment?

The parent field in ReviewComment points back to the same ReviewComment table. If parent is NULL, it's a top-level comment. If parent is set, it's a reply to that comment.

I limited it to 1 level of nesting — if someone tries to reply to a reply, my view checks if parent.parent_id is not None and rejects it. This keeps the UI simple and prevents deep threading mess.

Why did you use settings.AUTH_USER_MODEL instead of importing User directly in models?

Because if I import User directly and later someone changes which model is the auth user, all my FK references break. Using settings.AUTH_USER_MODEL is the Django best practice — it always points to whatever model is configured as the auth user in settings. It's like an indirect reference that stays correct even if the user model changes.

Why did you use db_index=True on certain fields?

I added indexes on fields that are frequently used in filtering and ordering — like title (search), release_date (ordering), is_released (filtering). An index makes database lookups on these fields much faster, like a book's index page.

Note: unique=True automatically creates an index, so I didn't add db_index separately for fields like tmdb_id.

What does the is_released flag control?

It controls the entire logic path. If is_released=True, the movie shows Opinion Meter (4-category voting) and allows reviews. If is_released=False, it shows Hype Meter (excited/not excited) and blocks reviews. This one boolean drives which features are available for each movie.

3. Query Optimization

What is the N+1 query problem and how did you solve it? HOT

N+1 means: 1 query to get a list of items, then N extra queries to get related data for each item. For example, if I have 20 movies and each has genres, without optimization Django fires 1 query for movies + 20 queries for genres = 21 queries.

I solve it with:

  • select_related("user") — For ForeignKey (one-to-one). It does a SQL JOIN and gets both tables in 1 query.
  • prefetch_related("categories") — For ManyToMany or reverse FK. It fires 2 queries total (1 for movies, 1 for all genres), then joins them in Python.

Example: In my movie detail view, I do Movie.objects.prefetch_related("categories", "cast__person", "crew__person") — this gets the movie + all cast + all crew in just a few queries instead of hundreds.

When do you use select_related vs prefetch_related? LIKELY

select_related = for ForeignKey or OneToOne. It does a SQL JOIN. Works in 1 query. Example: MovieReview.objects.select_related("user") — gets review + user in one query.

prefetch_related = for ManyToMany or reverse ForeignKey (one-to-many). It does a separate query and joins in Python. Example: Movie.objects.prefetch_related("categories").

Simple rule: If it's a "one" relationship → select_related. If it's a "many" relationship → prefetch_related.

How do you calculate vote percentages? Why not store them?

I calculate on every page load using database aggregation: MovieVote.objects.filter(movie=movie).values("vote").annotate(count=Count("id")). This gives me the count of each vote type in one query. Then I calculate percentages in Python.

I don't store percentages because they change every time someone votes. If I stored them, I'd have to update the percentage every time anyone votes — that's extra writes and risk of stale data. Calculating on-read is fast enough for my scale.

What is annotate() and how did you use it?

annotate() adds a computed field to each object in the queryset. For example, annotate(like_count=Count("likes")) counts the number of likes for each review at the database level — much faster than doing a Python loop.

I also used it for the trending section: annotate(vote_count=Count("votes")).filter(vote_count__gt=0).order_by("-vote_count") — this gets movies sorted by vote count, all in one query.

Explain the Prefetch object you used in the reviews.

Normal prefetch_related("likes") would fetch ALL likes. But I only need to know if the current user liked each review. So I used:

Prefetch("likes", queryset=ReviewLike.objects.filter(user=request.user), to_attr="user_likes")

This fetches only the current user's likes and stores them in review.user_likes attribute. Then bool(review.user_likes) tells me if the user liked it or not.

4. Voting System & Opinion Aggregation

How does vote switching work? What if a user changes their vote? LIKELY

I use MovieVote.objects.update_or_create(user=request.user, movie=movie, defaults={"vote": vote}). This does: if a vote exists for this user+movie, update it. If not, create a new one. It's atomic — one database operation handles both cases.

Combined with unique_together, this guarantees one vote per user per movie, and vote switching just works without any extra logic.

How does the hype voting work? What prevents hype votes on released movies?

In the hype_vote_movie view, I first check if movie.is_released and reject the request with an error message. Also, since hype votes are in a separate table (MovieHypeVote), the data model itself makes the intent clear — hype votes are a separate concept.

How do you handle the trending section on the home page?

I filter movies released in the last 120 days, annotate them with vote_count=Count("votes"), filter only those with at least 1 vote, and order by vote count descending. This is all done in one database query. The most voted recent movies appear first.

How does the hype score calculation work in the home page?

I used Django's Case/When expression with ExpressionWrapper to calculate the percentage at database level: excited_count * 100.0 / total_hype_votes. If total is 0, I default to 0 to avoid division-by-zero. This is all done in the SQL query, not in Python loops.

5. Custom User Model & Authentication

Why did you create a custom User model? HOT

Django's default user model uses username for login. I wanted email-based login because that's what modern apps use. I extended AbstractBaseUser and PermissionsMixin, set USERNAME_FIELD = 'email', and created a custom UserManager.

Django docs strongly recommend setting up a custom user model at the start of the project — changing it later is very painful because all migrations depend on the user model.

What is UserManager and why did you create it?

When you use a custom user model, Django's default create_user() and create_superuser() expect a username field. Since I use email instead, I had to write my own manager that handles create_user(email, password) and create_superuser(email, password).

In create_user, I validate email and password, normalize the email (lowercase the domain part), hash the password with set_password(), and save.

How does email verification work? LIKELY

1. User signs up → I create the user with is_email_verified=False

2. I generate a UID (base64 encoded user ID) and a token using Django's default_token_generator

3. I build a verification URL and send it via Brevo email API

4. When user clicks the link, I decode the UID, find the user, check the token

5. If valid, I set is_email_verified=True

6. During login, I check this flag — unverified users cannot login

The token is derived from the user's password hash and last login time, so it automatically expires if the password changes.

What is @login_required and what does it do?

It's a Django decorator that checks if request.user.is_authenticated. If not, it redirects to the login page. I also set LOGIN_URL = "login" in settings so Django knows where to redirect.

For the movie detail page, I did a manual check instead of using the decorator, because I wanted to add a custom message and append ?next=/movie/42/ to the login URL so the user is redirected back after logging in.

How does password reset work?

Same concept as email verification — generate UID + token, send a link via email. When user clicks, validate the token, show a password reset form, then call user.set_password(new_password) and save.

Important security detail: In the forgot password view, I always show the same message "If an account exists, a link has been sent" — this prevents attackers from figuring out which emails are registered (information leakage).

6. Django REST Framework & API Design

Why did you use DRF when you already have Django templates? LIKELY

The Django template views serve the web frontend. The DRF API serves any other client — mobile apps, frontend frameworks like React, third-party integrations. Having both means the same backend can serve any client without rebuilding.

Also, DRF gives me clean serializer pattern (separates presentation from models), built-in permission classes, and a browsable API for testing.

Explain your API authentication setup.

I use TokenAuthentication from DRF. When a user logs in via the API, I create or fetch a token using Token.objects.get_or_create(user=user) and return it. The client sends this token in the Authorization: Token xxx header for subsequent requests.

In settings, I set DEFAULT_PERMISSION_CLASSES = [IsAuthenticated] so all API endpoints require auth by default. Public endpoints explicitly set permission_classes = [AllowAny].

What are serializers and why did you use separate List and Detail serializers for Movie?

Serializers convert model instances to JSON (and validate incoming JSON). I have MovieListSerializer with fewer fields (for listing) and MovieDetailSerializer with more fields like overview (for detail page). This way, the list API doesn't send unnecessary data — keeping responses smaller and faster.

How does update_or_create work in ReviewCreateUpdateAPIView?

MovieReview.objects.update_or_create(user=request.user, movie_id=movie_id, defaults=serializer.validated_data)

It looks for an existing review by this user for this movie. If found, it updates the fields in defaults. If not found, it creates a new one. This is one API endpoint that handles both create and update — clean and simple.

7. AI Feature Integration

How did you integrate AI into the project? HOT

I use the Groq API which runs LLaMA models. I built a service layer (ai_service.py) that constructs prompts based on the user's review and the selected mode, calls the Groq API, and returns the result.

The AI is assistive — it helps users rewrite their reviews in different styles. The core opinion system works completely without AI. If AI goes down, nothing else breaks.

What is the fallback strategy in your AI service?

I have two models configured: llama-3.3-70b-versatile (primary) and llama-3.1-8b-instant (fallback). The code first tries the primary model. If it fails for any reason (timeout, rate limit, error), it catches the exception and tries the fallback model. This way the user still gets a response even if the main model is having issues.

How did you implement rate limiting for AI? LIKELY

Application-level rate limiting. I have an AIRequestLog model that stores every AI request with a timestamp. Before processing a new request, I count how many requests this user made for this action in the last 10 minutes. If it's 10 or more, I return a 429 Too Many Requests error.

AIRequestLog.objects.filter(user=user, action=action, created_at__gte=since).count()

This approach also gives me an audit trail — I can see who used AI, what they sent, what they got back, and if it failed.

Why do you log every AI request?

Three reasons: (1) Rate limiting — I count recent requests to enforce limits. (2) Auditing — I can see usage patterns, catch abuse. (3) Debugging — if something fails, the error message is logged, so I can see exactly what went wrong.

What are the 7 AI rewrite modes?

Rewrite (clean polished English), Shorten (under 180 chars), Funny, Roast (humorous, not abusive), Professional (formal tone), Hype (excited tone), and Savage 1-Star (brutal review, no hate speech). Each mode has a different prompt template in the build_prompt() function.

8. Forms, Validation & Security

Where does validation happen in your project? LIKELY

Multiple levels:

  • Database level — unique_together prevents duplicate votes/reviews. MaxLengthValidator on review text.
  • Form level — MovieReviewForm.clean_review_text() checks empty and length. SignupForm.clean_email() checks duplicate.
  • View level — I check request.method != "POST", validate vote choices against an allowed set, check text length for comments.
  • Serializer level — DRF serializers validate on is_valid(raise_exception=True).
How do you handle CSRF protection?

Django's CsrfViewMiddleware is enabled. Every form in the templates uses {% csrf_token %}. For AJAX requests (like the like button), the CSRF token is sent via JavaScript from the cookie. For the DRF API, Token Authentication is used instead of sessions, so CSRF is not needed there.

How do you prevent users from deleting other people's comments?

In delete_comment_page, I check two conditions: is the current user the comment owner, OR is the current user the review owner (review owners can moderate comments on their reviews). If neither is true, I return "Not allowed". This is an ownership check at the view level.

What is form.save(commit=False) and why did you use it?

In submit_review, the form has fields for rating, review_text, spoiler flag. But I also need to set user and movie — which are not form fields. So I do review = form.save(commit=False) to create the object in memory without saving to DB, then I set review.user and review.movie manually, then call review.save().

9. External Services (TMDB, Brevo, Supabase)

Why did you use TMDB API instead of letting users add movies? HOT

Because TMDB is an authoritative data source — movie titles, posters, release dates, cast, crew are all accurate and consistent. If I let users add movies, there would be duplicates, typos, wrong data. TMDB lets me focus on what my project is actually about — opinion aggregation — instead of building a content management system.

How does TMDB sync work?

I built a Django management command (python manage.py sync_tmdb_movies). It calls the TMDB API, gets movie data, and uses update_or_create with tmdb_id as the lookup field. So if a movie already exists, it updates the data; otherwise creates a new entry. Same for Person, Cast, Crew.

How does Supabase profile image upload work?

User uploads a file → I validate type (JPG/PNG/WEBP) and size (max 5MB) → Generate a unique filename using uuid4 → Read file bytes → Upload to Supabase Storage bucket → Get the public URL → Save URL in user's profile_image field.

I use Supabase because I don't want to store files on my server — it's cleaner and the files are served from Supabase's CDN.

Why Brevo for emails instead of Django's built-in email?

Django's send_mail() needs an SMTP server. Setting up a reliable SMTP that doesn't go to spam is hard. Brevo gives me a simple HTTP API — I just POST the email data and they handle delivery. It's more reliable for transactional emails like verification and password reset.

10. Deployment & Production Settings

How is your app deployed? LIKELY

Deployed on Render. I use Gunicorn as the WSGI server (Django's dev server is single-threaded and has no security features). WhiteNoise serves static files (CSS, JS, images) without needing a separate Nginx server.

How do you manage environment variables?

I use python-dotenv. All secrets (SECRET_KEY, database credentials, API keys) are in a .env file which is in .gitignore. In code, I use os.getenv("KEY") to read them. On Render, the same variables are set in the dashboard's environment variables section.

Why is DEBUG = False important in production?

With DEBUG=True, Django shows detailed error pages with your code, file paths, settings — an attacker can see everything. With DEBUG=False, users see a generic error page. Also, Django collects static files differently in production mode.

What is WhiteNoise and why do you need it?

In production, Django doesn't serve static files. You normally need Nginx for that. WhiteNoise is a middleware that lets Django serve static files efficiently. It compresses files and adds cache headers. This simplifies deployment — I don't need a separate web server.

What is the difference between STATIC_URL, STATICFILES_DIRS, and STATIC_ROOT?
  • STATIC_URL = '/static/' — The URL prefix in the browser. When the template says {% static 'style.css' %}, it becomes /static/style.css.
  • STATICFILES_DIRS — Where Django looks for static files during development (your source folders).
  • STATIC_ROOT — Where collectstatic copies ALL static files for production. WhiteNoise serves from here.

11. Trade-offs & "Why Not X?" Questions

Why no Redis/caching? HOT

Vote percentages change on every vote. If I cache them, I need to invalidate the cache every time someone votes — that's complex cache invalidation logic. PostgreSQL aggregations are fast for my current scale. Adding Redis would be premature optimization — solving a performance problem I don't have yet.

If the app grows, I would add caching for things that don't change often, like movie metadata from TMDB.

Why no Celery for background tasks?

The only async-ish operation is sending emails, and Brevo's API is fast (< 1 second). AI requests are synchronous because the user is waiting for the result on the page. If emails start taking too long or I add features like batch TMDB sync, I would add Celery then.

Why no WebSocket for real-time vote updates?

Real-time updates are a nice-to-have, not a need. Users vote and see the updated percentages on page reload. Adding WebSocket (Django Channels + Redis) is significant infrastructure complexity for a portfolio project. If this was a live competition voting app, I would add it.

Why no pagination in the API?

The template views have pagination (Paginator with 24 items per page). The API currently returns all results — this is a known limitation. In production, I would add DRF's PageNumberPagination to limit response size and improve performance.

Why function-based views instead of class-based views?

For the template views, function-based views are simpler and more readable for the kind of logic I have (multiple conditionals, enriching data, manual permission checks). The API views use class-based views (APIView, RetrieveAPIView) because DRF's class-based pattern fits well there.

Why no admin/moderator roles?

There's no user-generated content that needs moderation — movies come from TMDB, reviews and votes are user-owned. Django's built-in admin panel is sufficient for data inspection. Adding roles would be feature bloat for this project's scope.

12. Scenario / Thinking Questions

If 1 million users vote on a movie at the same time, what breaks? DEEP

The main bottleneck would be database writes — every vote is an INSERT or UPDATE. Solutions I would consider:

  • Database connection pooling (pgbouncer)
  • Pre-computed vote counts that update periodically instead of real-time
  • Caching the vote percentages in Redis with a short TTL, rebuilding every few seconds
  • Horizontal scaling with multiple Gunicorn workers behind a load balancer

But unique_together still protects against duplicate votes — that's database-level, so even under load, data integrity is maintained.

A user submits a review, but the save fails midway. What happens to the vote? DEEP

Currently, votes and reviews are independent operations — they happen in separate views. A review failure doesn't affect votes. But if I needed them to be atomic (both succeed or both fail), I would wrap them in from django.db import transaction and use with transaction.atomic():. This makes the database roll back all changes if anything inside fails.

How would you add a "Top Reviewers" leaderboard?

I'd query: User.objects.annotate(review_count=Count("moviereview"), total_likes=Count("moviereview__likes")).order_by("-total_likes")[:10]

This gets users with the most liked reviews. All done in one database query using annotate. If it gets slow, I'd cache the result since the leaderboard doesn't need real-time accuracy.

What if the Groq AI API goes down permanently? DEEP

The core app still works — voting, reviews, watchlist, everything. AI is assistive, not core. In code, the AI errors are caught and return a 500 to the frontend, which shows "AI failed" — but nothing breaks. I could also swap to another LLM provider (OpenAI, Anthropic, local Ollama) by just changing the groq_chat() function. The rest of the code doesn't care which AI provider is used.

How would you add unit tests to this project?

I would test at multiple levels:

  • Model tests — Verify unique_together constraints, test that creating duplicate votes raises IntegrityError
  • View tests — Use Django's TestClient to test vote submission, review CRUD, auth-required redirects
  • API tests — Use DRF's APIClient with token auth to test all endpoints
  • Service tests — Mock the Groq API and test the AI service logic without making real API calls
If you had to rebuild this project from scratch, what would you change?

A few things:

  • Add API pagination from the start
  • Use UniqueConstraint instead of deprecated unique_together
  • Add Django signals to auto-update denormalized counts if needed
  • Write tests from day one
  • Use environment-specific settings files (dev, staging, prod) instead of one settings.py
What is the difference between get_object_or_404 and .filter().first()? When do you use which?

get_object_or_404 returns the object or raises a 404 error. I use it when the object MUST exist — like viewing a movie detail page. If the movie doesn't exist, showing a 404 is correct.

.filter().first() returns the object or None. I use it when the absence is expected — like checking if a user already voted. No vote is not an error, it just means they haven't voted yet.

Explain the difference between auto_now and auto_now_add.

auto_now_add=True — Sets the timestamp only when the object is first created. Used for created_at.

auto_now=True — Updates the timestamp every time the object is saved. Used for updated_at.

I used auto_now_add on all my created_at fields and auto_now on the Movie's updated_at field.

What is related_name and why is it important?

related_name is the reverse accessor name. If MovieVote has movie = ForeignKey(Movie, related_name="votes"), then I can do movie.votes.all() to get all votes for that movie. Without it, Django would auto-generate movie.movievote_set.all() which is ugly and less readable.

13. SQL JOINs & Django Optimization

SQL JOIN Basics

INNER JOIN

INNER JOIN returns only matching rows from both tables.

SELECT customers.name, orders.product
FROM customers
INNER JOIN orders
ON customers.id = orders.customer_id;

Result: Only customers who have orders will appear.

LEFT JOIN

LEFT JOIN returns all rows from the left table and matching rows from the right table. If no match exists, NULL is returned.

SELECT customers.name, orders.product
FROM customers
LEFT JOIN orders
ON customers.id = orders.customer_id;

Result: All customers appear, even those with no orders.

RIGHT JOIN

RIGHT JOIN returns all rows from the right table and matching rows from the left table.

SELECT customers.name, orders.product
FROM customers
RIGHT JOIN orders
ON customers.id = orders.customer_id;

The N+1 Query Problem

Suppose we fetch all orders and access customer data inside a loop.

orders = Order.objects.all()

for order in orders:
    print(order.customer.name)

Database queries:

  • 1 query to fetch all orders
  • N queries to fetch customer for each order

Total = N + 1 queries. This is inefficient.

select_related()

Used for ForeignKey and OneToOne relationships. It performs a SQL JOIN and fetches related data in a single query.

orders = Order.objects.select_related("customer")

Internally runs:

SELECT order.*, customer.*
FROM order
INNER JOIN customer
ON order.customer_id = customer.id;

Only 1 database query is executed.

prefetch_related()

Used for Many-to-Many or reverse ForeignKey relationships. It executes separate queries and joins them in Python.

customers = Customer.objects.prefetch_related("order_set")

Internally runs:

SELECT * FROM customer;

SELECT * FROM order
WHERE customer_id IN (...);

Django matches results in memory.

Uses SQL JOIN Yes No
Number of Queries 1 2
Best For ForeignKey, OneToOne ManyToMany, reverse FK
